# 前回完了日からN日後の繰り返し

- 文書状態: 確定（実装・動作確認対象）
- 最終更新日: 2026-11-13
- 対応Issue: #355

## 1. 設定と基準日

- 安定コードは`after_completion_days`、パラメータは`intervalDays`（1～999の整数）とする。
- 開始日基準の`every_n_days`とは別方式とし、既存の計算・保存値は変更しない。
- 保存済みの完了・スキップがない場合、初回の実行日は開始日とする。
- 以後は同じTODOの最も新しい完了・スキップの解決論理日からN日後を、次の実行日とする。
- 解決論理日は操作時の共通終了時刻で決定し、カレンダー日や24時間の加算では計算しない。タイムゾーンや終了時刻の変更後も、保存済みの論理日を再解釈しない。
- 既存TODOをこの方式へ変更した場合も、同じTODOの保存済み完了・スキップを使用する。タイトル・通知等の編集だけで起点をリセットしない。開始日を変更した場合、次回日が開始日より前になるときは開始日を使用する。
- スキップは完了数へ加算せず、履歴も`skipped`のまま保存するが、次のサイクルの起点としては完了と同様に扱う。

例: 11月13日開始・N=3で、未完了のまま11月17日に完了した場合、次回は11月20日。開始日基準の11月19日へ進めない。

## 2. 未完了と有効期間

- 「未完了の場合、完了するまで表示」は必須ONとし、編集画面ではチェック済み・変更不可のスイッチと理由を表示する。RepositoryでもONを保証する。
- 実行日を過ぎても同じ1回分を表示し、未完了履歴、後続予定や行を日数分生成しない。整合処理前でも一覧・ウィジェットに同じ保留分を表示できる。
- 完了・スキップするまでは次の1回より先の予定は不明とする。未来の仮の完了日を置いて予定を展開しない。
- 次回実行日が終了日を超える場合、新しいサイクルを作らない。ただし終了日以前に到来した未解決の1回分は終了日後も解決まで表示する。
- アーカイブ中は表示・通知を止め、復元時は同じ保存済み履歴から未解決の1回分だけを再計算する。アーカイブ中や長期未起動中の予定・未完了履歴は補完しない。
- 既存の「未完了TODOに表示しない」は未完了一覧の確認済み境界だけに作用し、この方式の起点や通常一覧での繰り越しを変更しない。

## 3. 完了・スキップと取り消し

- 一覧、通知、ウィジェットは同じRepository操作を使用する。元の実行日、解決日と操作IDを同一トランザクションで保存する。
- 解決後は未来の次回を再計算し、同じ論理日の二重完了・二重スキップや古い予定への遅延操作を拒否する。
- 取り消しの入口・許可期間は既存仕様を維持する。通常は現在の論理日に解決した記録だけをカレンダー履歴から取り消せる。
- 取り消した記録を除いた履歴から起点を再計算し、対象の未完了を再表示する。取り消せない過去の確定履歴を巻き戻したり削除したりしない。
- 取り消しのUndoで元の記録を復元した場合も、同じ履歴から次回を再計算する。

## 4. 共通計算・通知・表示

- 次回実行日は純粋なドメイン関数で計算する。保存するのはTODO定義と解決履歴であり、次回日や別の起点を新しい永続列として二重保存しない。
- 一覧・カテゴリ別一覧・編集プレビュー・通知・ウィジェットへ、最新の解決論理日を計算コンテキストとして渡す。
- 編集プレビューには確定できる次回1件と説明を表示する。すでに繰り越し中なら元の実行日を表示する。間隔が不正な場合は保存しない。
- 次回日の期限時刻・事前・期限超過通知を既存の通知ルールで計算する。解決で残通知を取り消し、次回の候補を登録する。未完了を理由に未来のサイクルを仮定したり、経過通知を毎日再登録したりしない。
- ウィジェットの通常読取期間より古い起点も、対象TODOの直近の解決記録を追加取得して反映する。全履歴を日別予定へ展開しない。
- 履歴とアーカイブ詳細の繰り返し表示でも新方式を識別できるようにする。

## 5. 保存互換性と試験

- Roomの既存文字列コード・JSONパラメータ・履歴日付を使用し、永続列とRoomスキーマ番号は増やさない。
- バックアップ書出しは[形式7](../backup-specs/format-v7.md)とする。形式1～6は従来どおり読み込み、新方式を旧形式として偽装した入力は拒否する。
- 既存の確定履歴・公開済み成果物・過去の試験合格記録を変更しない。
- 追加の確認項目は[Issue #355試験項目](../../test-specs/completion-recurrence-355.md)へ記録し、既存424件の実績へ流用しない。

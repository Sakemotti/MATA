# MATA 手動バックアップ復元仕様

- 文書状態: 初版
- 最終更新日: 2026-08-10

## 1. 基本動作

- 設定画面の「バックアップから復元」から開始する。
- 復元はバックアップ対象データの完全置換とし、現在データとのマージ、重複解消の選択、項目単位の選択復元は提供しない。
- 復元後にユーザーが実行できる「元に戻す」は提供しない。
- ファイル選択、検証、確認が完了するまで現在データを変更しない。

## 2. ファイル選択

- Storage Access Frameworkの`ACTION_OPEN_DOCUMENT`を使用する。
- MIMEタイプは`application/zip`を基本とし、DocumentProviderが独自拡張子を絞り込めない場合も選択後の内容検証を正とする。
- ストレージ全体への読み取り権限を要求しない。
- `.mata-backup`は選択時の目安とし、拡張子だけで有効と判断しない。
- 選択をキャンセルした場合はエラーを表示せず設定画面へ戻る。
- 選択URIの永続化可能な権限は復元処理中だけ保持し、成功、失敗、または回復処理完了後に解放する。

## 3. 検証用一時領域

- 選択ファイルを信頼できない外部入力として扱う。
- ZIPを任意のファイルシステムパスへ展開しない。
- `data.json`だけをアプリ専用の一時領域へストリーミングし、同時にCRC、SHA-256、サイズを検証する。
- `manifest.json`は上限内で読み取り、厳密なJSONデコーダーで解析する。
- 一時データには処理IDに基づくアプリ内部名を使い、外部のエントリ名をファイル名へ使用しない。
- 検証成功後の取り込みも一時データからストリーミングする。
- 成功、失敗、強制終了後の回復のいずれでも一時データを削除する。

## 4. 構造検証

次を確認する。

1. ZIPとして正常に読み取れる。
2. エントリが`data.json`、`manifest.json`の2件だけで、順序も仕様どおりである。
3. 重複、未知、ディレクトリ、危険なパス名のエントリがない。
4. 各エントリが許容サイズ、圧縮率、JSON深度などの安全上限内である。
5. ZIP CRCが一致する。
6. manifestの必須フィールド、型、値、形式ID、形式バージョンが正しい。
7. `data.json`の非圧縮バイト数とSHA-256がmanifestに一致する。
8. manifestの件数がdata内の各配列件数と一致する。

構造検証に失敗した場合は意味検証へ進まず、現在データを一切変更しない。

## 5. 互換性検証と移行

- 読み込み実装が`formatVersion`を認識し、`minimumReaderVersion`を満たすことを確認する。
- 作成アプリのバージョン名、バージョンコード、Roomスキーマバージョンの違いだけでは拒否しない。
- 対応済みの古い形式は、形式ごとに定義した移行処理を1バージョンずつ適用する。
- 各移行段階の入力と出力を検証する。
- 未対応の新形式、未知のminimum reader要件、欠けた移行経路、移行失敗は復元を拒否する。
- 未知の値を現在値や初期値へ推測変換しない。

## 6. 意味検証

移行後のデータ全体に対して次を確認する。

### 6.1 JSONと値

- 必須フィールド、型、明示的なnull、未知フィールド、重複キー
- canonical UUID、ISO日付、UTC Epochミリ秒、時刻範囲
- 文字列長、列挙コード、配列件数、整数範囲
- カテゴリ名の正規化結果と重複
- カテゴリの色、アイコン、並び順、終了時刻
- TODOの開始日、終了日、期限、定義リビジョン
- 繰り返し方式、パラメータバージョン、方式固有パラメータ
- 通知の種別、数値、単位、TODO内上限、重複、並び順
- 実行状態、操作時点、確定時点、論理日、一意条件
- 期間種別、期間境界、必要回数、完了回数、達成判定、表示日、一意条件
- 履歴スナップショットのバージョン、構造、親レコードとの一致
- 実行状態のリビジョン、日付、TODOとの一致
- 一般設定の時刻、曜日、真偽値、テーマ

### 6.2 IDと参照

- 各データ種別内でIDが重複しない。
- `operationId`が重複しない。
- TODOの`categoryId`が`null`または存在するカテゴリを参照する。
- 通知、実行記録、期間結果、実行状態が存在するTODOを参照する。
- TODOごとの通知、履歴、期間結果、実行状態が一意制約を満たす。
- 完全削除済みのTODOや存在しないカテゴリを暗黙に作成しない。

### 6.3 整合性

- manifest件数と、移行後に復元する件数が一致する。旧形式移行で件数が変わる仕様の場合は移行定義の期待件数と照合する。
- `achieved`が完了数と必要回数から算出した値に一致する。
- `normalizedName`がカテゴリ名から再計算した値に一致する。
- `definitionRevision`と`appliedDefinitionRevision`が参照TODOの現在リビジョンを超えない。
- スナップショット内のTODO ID、定義リビジョン、論理日または期間境界が親レコードと一致する。

1件でも失敗した場合は復元を開始しない。検証済みの一部だけを採用しない。

## 7. 復元確認

すべての検証に成功した後、確認ダイアログへ次を表示する。

- バックアップ作成日時
- 作成時のアプリバージョン
- TODO総数
- アーカイブ済みTODO数
- カテゴリ数
- 通知設定数
- 完了、スキップ、未完了を合計した実行履歴数
- 期間結果数
- 現在のTODO、カテゴリ、履歴、対象設定がすべて置き換わること
- 復元完了後に元へ戻せないこと
- バックアップファイルがアプリ独自には暗号化されていないこと

操作は「復元する」と「キャンセル」とし、確認文字列の入力は要求しない。キャンセルした場合は一時データとURI権限を解放し、現在データを変更せず設定画面へ戻る。

## 8. 復元前準備

ユーザーが「復元する」を選択した後に次を行う。

1. バックアップ・復元用の排他ロックを取得する。
2. TODO、カテゴリ、履歴、対象設定を変更する操作を無効にする。
3. 処理ID、段階、入力URIをアプリ専用の操作ジャーナルへ保存する。
4. 現在のバックアップ対象データから、アプリ専用領域にロールバック用スナップショットを作成して検証する。
5. 現在OSへ登録しているMATAの通知アラームと表示中通知を取り消す。

ロールバック用スナップショットはユーザー向けバックアップと同等のデータを持つが、復元処理専用のアプリ内部ファイルとする。アプリ専用領域に保存し、復元成功またはロールバック完了後に削除する。

## 9. 全置換

- 検証済みデータを一度にメモリへ読み込まず、アプリ専用一時データから順次取り込む。
- Roomのカテゴリ、TODO、通知設定、実行記録、期間結果、実行状態を1つのデータベーストランザクションで全置換する。
- 外部キー検査と一意制約を有効にした状態で取り込む。
- Room反映後にバックアップ対象のDataStore設定を反映する。
- RoomとDataStoreをまたぐ処理は操作ジャーナルとロールバック用スナップショットによる二相の回復手順で管理する。
- DataStore反映完了前は置換済みデータを通常UI、通知、ウィジェットへ公開しない。
- 全データ反映後に再度、件数、参照、一意制約、設定値を検証してからコミット済み段階へ進める。

Google Playの購入状態、祝日キャッシュ、通知権限、正確なアラーム権限、ウィジェット配置は置き換えない。

## 10. 失敗とロールバック

- RoomまたはDataStoreの反映、整合検証、後続の必須処理に失敗した場合は、ロールバック用スナップショットから復元前のRoomとDataStoreへ戻す。
- Roomトランザクション内の失敗はそのトランザクションをロールバックする。
- Roomコミット後にDataStoreが失敗した場合は、ジャーナルをロールバック要求へ更新してから旧Roomと旧DataStoreを復元する。
- ロールバック後は復元前データに基づき将来通知とウィジェットを再構築する。
- ロールバック自体を再実行しても同じ復元前状態になるよう冪等にする。
- 失敗理由と、元のデータへ戻したことをユーザーへ表示する。
- 一部だけ復元された状態で通常画面を操作可能にしない。

## 11. 強制終了後の回復

アプリの通常データ公開より前に操作ジャーナルを確認する。

| ジャーナル状態 | 回復動作 |
| --- | --- |
| 検証中・確認待ち | 一時データを削除し、現在データを維持 |
| 置換開始前 | ロールバック用データを削除し、現在データを維持 |
| Room置換中 | Roomトランザクションの結果を確認し、復元前状態へ戻す |
| Room置換済み・DataStore未完了 | ロールバック用データからRoomとDataStoreを復元 |
| データ置換済み・再構築前 | 復元データを再検証し、成功なら再構築を再開。不整合なら復元前へ戻す |
| 完了記録済み | 後始末を再実行して復元済み状態を維持 |

回復が完了するまでTODO一覧など通常画面を表示しない。最終状態は復元前または復元完了のどちらかとし、部分状態を残さない。

## 12. 長時間処理と進捗

- 復元処理は固有名のユニークな`CoroutineWorker`で実行する。
- 数分を超える可能性がある場合は長時間実行Workerへ移行し、必要なフォアグラウンド通知を表示する。
- ユーザーが復元を確定した後は、完了またはロールバック終了までUIからキャンセルできない。
- WorkManagerから停止要求を受けた場合は安全な境界で停止し、次回実行または起動時の回復に必要なジャーナルを残す。
- 画面回転、構成変更、バックグラウンド移行、プロセス再生成後も処理IDから状態を再取得する。
- 「準備中」「データを復元しています」「通知とウィジェットを更新しています」「元の状態へ戻しています」を区別して表示する。

## 13. 復元後の再構築

データ全置換が成功した後、次の順で現在環境へ適用する。

1. Google Playの現在の購入状態を維持する。
2. 端末内の有効な祝日キャッシュは維持し、必要な年が不足する場合は共通祝日取得処理を予約する。
3. 確定済みの論理日、実行履歴、期間結果を変更しない。
4. 現在の端末時刻、タイムゾーン、復元設定、祝日情報から現在と将来を再計算する。
5. 実行状態を履歴に対して再検証し、必要なら安全な位置から整合処理を再開する。
6. 現在の通知権限と正確なアラーム権限に従い、将来の通知だけを再登録する。
7. 経過済みの通知を復元直後に発火させない。
8. 全ウィジェットの表示データを再構築して更新する。
9. 復元されたテーマと表示設定をアプリ全体へ即時反映する。
10. ナビゲーション状態を再構成し、TODO一覧の日付別表示へ移動する。

通知やウィジェットの一時的な外部更新失敗は、データ置換自体を破損扱いにしない。再試行Workを登録し、復元完了メッセージと併せて更新待ちであることを通知する。

## 14. 成功と後始末

- データ置換と必須の整合確認後、ジャーナルを完了へ更新する。
- 入力URIの権限、検証用一時データ、ロールバック用スナップショット、排他ロックを解放する。
- TODO一覧へ「バックアップを復元しました」と表示する。
- 復元したファイルのURIや内容を履歴として保持しない。

## 15. 受け入れ条件

1. 拡張子ではなくファイルの構造と内容で有効性を判定できる。
2. 構造、ハッシュ、形式、型、値、参照、件数を現在データ変更前に検証できる。
3. 対応する旧形式を段階的に移行し、未対応形式を拒否できる。
4. 復元対象の概要と全置換、取り消し不可を確認前に表示できる。
5. RoomとDataStoreを部分公開せず全置換できる。
6. 途中失敗時に復元前の状態へロールバックできる。
7. 強制終了後に復元前または復元完了の一貫した状態へ回復できる。
8. Google Play購入状態と再生成可能な内部状態をバックアップ値で上書きしない。
9. 復元後に現在環境から将来通知とウィジェットを再構築できる。
10. 経過済み通知を復元直後に発火させない。

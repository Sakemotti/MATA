# MATA 通知再登録・テスト仕様

- 文書状態: 初版
- 最終更新日: 2026-08-26
- 対応する決定事項: 通知質問 87～120、125～130、136～146

## 1. NotificationReconciler

通知候補の登録、取消、再登録をNotificationReconcilerへ集約する。

- 画面、ViewModel、通知Receiver、起動処理はAlarmManagerを直接操作しない。
- ドメイン計算結果、通知設定、Androidの権限状態を入力とする。
- AlarmManagerを操作した結果をScheduledNotificationEntityへ反映する。
- 同じ入力で複数回実行しても同じ登録状態になる。

## 2. 差分再構成

### 2.1 手順

1. 処理開始時点のClock、ZoneId、権限、チャンネル状態を取得する。
2. 対象TODOと通知設定をページ単位で読み込む。
3. ドメイン計算エンジンから次回候補を取得する。
4. ScheduledNotificationEntityの登録済み候補と比較する。
5. 不要、変更済み、旧リビジョンのアラームを取り消す。
6. 不足している候補を正確または通常方式で登録する。
7. 成功・失敗状態を保存する。
8. 不要になった内部記録を保守対象へ移す。

現在時刻以前の候補は登録しない。

完了またはスキップ記録がある論理日は、将来アラームの取消に加えて、通知ドロワーへ表示済みの同一TODO・同一論理日のリマインダーも消去する。表示通知はTODO IDと論理日を含む内部タグで識別し、別TODO・別論理日の通知を巻き込まない。

### 2.2 対象範囲

通常操作では影響範囲を限定する。

| 変更 | 再構成対象 |
| --- | --- |
| TODO登録・編集 | 対象TODO |
| 完了・スキップ・それらの取り消し | 対象TODOと現在期間 |
| アーカイブ・復元・削除 | 対象TODO |
| カテゴリ終了時刻変更 | 所属する通常・アーカイブ復元対象TODO |
| カテゴリ削除 | 元の所属TODO |
| 共通終了時刻変更 | categoryIdがnullのTODO |
| 週開始曜日変更 | N週間にX回TODO |
| 祝日更新 | 平日または土日祝の対象日条件を使うTODO |
| 通知権限・チャンネル変更 | 通知付きTODO全件 |
| 正確なアラーム権限変更 | 通知付きTODO全件 |
| 時刻・タイムゾーン変更 | 通知付きTODO全件 |
| バックアップ復元 | 全件 |

## 3. 実行契機

### 3.1 端末とアプリ

次を契機に再構成する。

- アプリ起動
- フォアグラウンド復帰
- Androidの通知設定画面から復帰
- 正確なアラーム設定画面から復帰
- BOOT_COMPLETED
- ユーザーの初回ロック解除
- MY_PACKAGE_REPLACED
- 端末時刻変更
- タイムゾーン変更
- SCHEDULE_EXACT_ALARMの許可取得通知
- バックアップ復元成功

### 3.2 再起動

AlarmManagerの登録は端末再起動で消えるため、BOOT_COMPLETED後に再構成する。

- アプリが少なくとも1回起動済みであることを前提とする。
- データへアクセスできない場合は初回ロック解除後まで延期する。
- `ScheduledNotificationEntity.state`が`scheduled`のまま残っていても、OS登録済みの根拠として再利用しない。
- 端末イベント後の再構成では、将来候補のPendingIntentを取り消してから同じrequestCodeで再登録する。
- 経過済み候補を発火させない。
- 現在時刻より後の候補だけを登録する。

### 3.3 Receiverの有効化

- 通知付きTODOが0件なら再起動Receiverを無効化する。
- 最初の通知付きTODO保存時に有効化する。
- 最後の通知付きTODOが削除、アーカイブ、通知なしへ変更された場合は、全アラームを取り消して無効化する。
- 有効状態は端末再起動後も維持されるAndroidのComponent設定を使用する。

## 4. 権限変更

### 4.1 通知権限とチャンネル

- フォアグラウンド復帰時にAndroidから状態を再取得する。
- 未許可またはチャンネル無効ならOSアラーム登録を停止する。
- 通知設定自体は削除しない。
- 再び有効になった場合は将来候補だけを登録する。
- チャンネルを削除・再作成して無効設定を回避しない。

### 4.2 正確なアラーム

許可取得時:

1. canScheduleExactAlarmsを再確認する。
2. 登録済み通常アラームを取り消す。
3. 同じ将来候補を正確な方式で登録する。

許可取消時:

- Androidによって将来の正確なアラームが取り消されることを前提とする。
- 次回起動・復帰時に許可状態を検出する。
- ScheduledNotificationEntityを再検証する。
- 将来候補を通常方式で再登録する。

## 5. 時刻とタイムゾーン

時刻またはタイムゾーン変更時:

- 確定済み履歴を変更しない。
- 登録済みの将来アラームを取り消す。
- 新しいClockとZoneIdで期限と通知候補を再計算する。
- 新しい現在時刻以前の候補を飛ばす。
- 端末時刻が過去へ戻っても、配信済み候補を重複発火させない。

夏時間の欠落・重複時刻はドメイン仕様の規則に従う。

## 6. WorkManager

### 6.1 用途

AlarmManagerは通知時刻の起動だけに使用する。次はWorkManagerで処理する。

- 全件または大量の通知再構成
- バックアップ復元後の全件登録
- 一時的な登録失敗の再試行
- BroadcastReceiver内で完了できない長時間処理

### 6.2 固有Work

通知再構成には安定した固有名を使用する。要求が連続した場合は最新のデータ状態を対象とする1件へまとめる。

- Workの入力へ大量のTODOデータを渡さない。
- Work開始後にRepositoryから最新状態を取得する。
- 画面のライフサイクルに依存しない。
- アプリがバックグラウンドへ移動しても継続する。
- 端末イベントReceiverは全件再登録Workを開始して速やかに終了する。
- AlarmManager登録失敗が残る場合は指数バックオフで最大5回実行する。

### 6.3 ページ処理

- 全件を一度にメモリへ読み込まない。
- 安定したID順でページ処理する。
- ページごとに差分登録と内部状態保存を確定する。
- 中断後は安全に最初から再比較でき、重複登録しない。

## 7. 障害処理

### 7.1 正確なアラーム

登録直前に権限を再確認する。SecurityExceptionまたは権限不一致の場合は通常方式へフォールバックし、処理全体をクラッシュさせない。

### 7.2 一時的な登録失敗

- ScheduledNotificationEntityをfailedにする。
- 失敗理由をユーザーデータを含まないコードで保存する。
- WorkManagerの指数バックオフで再試行する。
- 成功済みの他候補を取り消さない。
- 設定画面に「一部の通知を登録できませんでした」と再試行操作を表示する。

### 7.3 データベース障害

- データを読み込めない場合は推測で通知を表示または登録しない。
- 既存のアラームを受信しても最新状態を検証できなければ通知を表示しない。
- 復旧後に全件再構成する。

### 7.4 祝日

- 通知Receiver内で祝日を取得しない。
- 取得済みキャッシュだけを使用する。
- 祝日更新後は平日または土日祝の対象日条件を使うTODOを再構成する。
- 更新処理に失敗した場合は既存予定を維持して再試行する。

### 7.5 force stop

ユーザーがAndroid設定などからアプリをforce stopした場合、AndroidがアプリのアラームとReceiver実行を抑止するため通知を保証しない。

次回ユーザー起動時:

- 経過済み通知を発火させない。
- 最新状態を整合する。
- 将来候補だけを再登録する。

## 8. バックアップ復元

復元時:

1. 復元前データに基づく全アラームを取り消す。
2. ScheduledNotificationEntityをクリアする。
3. TODO、カテゴリ、設定、履歴をトランザクションで復元する。
4. 現在の権限、時刻、タイムゾーン、祝日情報を取得する。
5. 復元されたTODOから将来候補を全件再構成する。
6. 経過済み通知を発火させない。

広告購入状態と祝日キャッシュは復元データで置き換えない。

## 9. 性能

- 通知設定数にプロダクト上の固定上限を設けない。
- OS登録数は通知設定1件につき最大1件とする。
- 無期限TODOの次回候補は繰り返し方式ごとの直接計算で求める。
- データベース検索にはtodoId、notificationSettingId、triggerAt、stateのインデックスを用意する。
- 全件再構成はページ単位で行う。
- 実装時に大量TODOで処理時間、メモリ、AlarmManager呼び出し数を計測する。

## 10. プライバシーとログ

- 通知配信状態と操作履歴を外部サーバーへ送信しない。
- リリースログへタイトル、説明、カテゴリ名、通知本文を出力しない。
- エラーコード、候補キーの匿名化表現、処理件数だけを診断可能にする。
- 内部通知記録は手動バックアップへ含めない。
- OSの通知履歴に残る内容はAndroidとユーザー設定の管理範囲とする。

## 11. デバッグ診断

デバッグ版だけに通知診断表示を用意する。

表示候補:

- TODO IDの短縮表現
- 対象論理日
- 次回登録時刻
- exactまたはinexact
- ScheduledNotificationEntityのstate
- 定義リビジョン
- 最終再構成時刻
- 失敗コード

タイトル、説明などのユーザー入力内容を診断ログへ不要に複製しない。公開版では診断画面と入口を表示しない。

## 12. テスト構成

AlarmManager操作をインターフェース化し、Fake実装で登録、取消、差分再構成を検証する。Clock、ZoneId、権限、チャンネル、WorkManager実行条件も差し替え可能にする。

### 12.1 ローカル単体テスト

- before、at、after
- 分、時間、カレンダー日
- 重複判定
- 論理日開始前の事前通知
- 論理日終了後の無効通知
- 終了境界5分以内と5分超過
- 次回候補探索
- 週X回・月X回の達成と取り消し
- 定義リビジョン不一致
- exactとinexactの選択
- 差分再構成の冪等性
- DBが`scheduled`でもOS登録が消失した場合に、端末イベント用再構成では再利用せず登録し直すこと
- requestCode衝突

### 12.2 API別テスト

- API 26～32: POST_NOTIFICATIONS要求なし
- API 33以降: 未選択、許可、拒否
- 正確なアラーム: 許可、未許可、実行中の取消
- チャンネル: 有効、サイレント、無効

### 12.3 端末イベント

- 端末再起動
- 初回ロック解除
- アプリ更新
- 端末時刻変更
- タイムゾーン変更
- 夏時間境界
- Doze中のexactとinexact
- force stop後の起動

### 12.4 操作競合

- 通知完了の連打
- 画面と通知からの同時完了
- ウィジェットと通知からの同時完了
- 通知完了後に確認通知と取り消し操作が表示されないこと
- 旧バージョンの取り消しPendingIntentを受信してもTODO状態を変更しないこと
- 編集、削除、アーカイブ直後に届く旧通知
- グループ通知の個別操作

### 12.5 統合テスト

通知設定保存から次を通して確認する。

1. ドメイン期限計算
2. 通知候補計算
3. ScheduledNotificationEntity保存
4. AlarmManager登録
5. Receiver受信
6. 最新状態再検証
7. Notification表示
8. 完了または消去
9. 次回候補登録

### 12.6 性能テスト

- 大量TODO
- TODOごとの複数通知
- 長期未起動後の再構成
- バックアップ復元後の全件登録
- ページ処理中断と再開

処理時間、最大メモリ、OS登録件数、重複候補数を計測する。

## 13. ユーザーへの説明

設定画面と動作確認項目書に次を記載する。

- 通常通知は時刻が遅れる可能性がある。
- force stop中は通知できない。
- Do Not Disturb、マナーモード、チャンネル設定に従う。
- 端末メーカー独自の省電力制御により遅れる場合がある。
- バッテリー最適化除外を必須にしない。

## 14. 受け入れ条件

1. すべての再構成契機から同じNotificationReconcilerを呼び出せる。
2. 同じ再構成を繰り返してもOS登録が重複しない。
3. 再起動、アプリ更新、時刻・タイムゾーン変更後に将来通知を復元できる。
4. 権限変更時にexactとinexactを安全に切り替えられる。
5. 一部失敗を他の成功候補から分離して再試行できる。
6. 大量データをページ単位で再構成できる。
7. 経過済み、対象外、編集済み、削除済み、アーカイブ済みTODOを誤通知しない。
8. force stopなどAndroid上保証できない状況をユーザーへ説明できる。
9. 通知設定から次回候補登録までを自動テストできる。
10. リリース版でユーザー入力内容をログまたは外部送信しない。

# MATA 祝日データ取得・キャッシュ仕様

- 文書状態: 初版
- 最終更新日: 2026-08-10

## 1. 目的と責務

日本の祝日情報を共通Repositoryで取得、検証、保存し、すべての利用箇所へ同じ祝日集合と取得状態を提供する。

- TODO編集、一覧、カレンダー、通知、ウィジェットは共通Repositoryを使用する。
- 各画面、Receiver、Workerが独自にAPIへ接続しない。
- 繰り返し計算処理内からネットワーク取得を開始しない。
- 計算処理には祝日集合と取得状態を不変の入力として渡す。

## 2. 対象となる祝日

- 日本の国民の祝日、振替休日、国民の休日を扱う。
- 年末年始の独自休業日、会社、学校、ゲーム内イベントなどの休日は扱わない。
- 祝日を除外するのは`weekdays`のTODOだけとする。
- `selected_weekdays`を含む他の繰り返し方式は、祝日を理由に除外しない。

## 3. データソース

| 項目 | 値 |
| --- | --- |
| サービス | Holidays JP API |
| URL | `https://holidays-jp.github.io/api/v1/date.json` |
| 形式 | 日付をキー、祝日名を値とするJSONオブジェクト |
| 取得範囲 | 前年、今年、翌年 |
| 対象年基準 | `Asia/Tokyo` |
| 認証 | なし |

- API以外の祝日サービスへ自動的に切り替えない。
- データソースを変更する場合は別途仕様変更とする。
- 対象年はリクエスト開始時の日本標準時の日付から固定し、処理途中で年を取り直さない。
- 祝日判定自体は時点ではなく`LocalDate`で行う。

## 4. HTTP通信

### 4.1 セキュリティ

- HTTPSだけを許可する。
- HTTPへのダウングレードリダイレクトを拒否する。
- HTTPSリダイレクトは最大5回まで許可する。
- Androidのcleartext通信をアプリ全体で無効にする。
- APIキー、Cookie、Referer、ユーザーデータ、端末固有IDを送信しない。

### 4.2 リクエスト

- `Accept: application/json`を送信する。
- User-Agentにはアプリ名とバージョンだけを含められる。
- gzipなどのHTTP圧縮を許可する。
- 従量制ネットワークでも取得を許可する。
- Wi-Fi、充電中、アイドル中、バッテリー残量などの追加制約は設けない。

### 4.3 タイムアウトとサイズ

| 項目 | 値 |
| --- | --- |
| 接続タイムアウト | 10秒 |
| 読み取りタイムアウト | 30秒 |
| 展開後レスポンス最大サイズ | 1 MiB |

Content-Lengthや圧縮前サイズだけを信用せず、読み取り中の展開後バイト数が上限を超えた時点で中止する。

## 5. 条件付きリクエスト

- APIから提供された`ETag`と`Last-Modified`を保存する。
- 次回取得では`If-None-Match`と`If-Modified-Since`を使用する。
- 対象となる3年分のキャッシュがすべて存在し、同じレスポンス検証情報に対応する場合だけ条件付きリクエストを使用する。
- HTTP 304ではHolidayEntityを変更せず、対象年の最終確認日時と取得結果だけを更新する。
- 必要なキャッシュが欠けた状態で304を受信した場合は、条件付きヘッダーを外して1回だけ再取得する。

## 6. 取得契機

次の場合に取得要求を発行する。

- 初回起動時に取得可能範囲内の必要年が未取得。
- アプリ起動時に、最後の正常確認から7日以上経過している。
- TODO編集や表示計算で、取得可能範囲内の未取得年が必要になった。
- 7日ごとの定期更新時刻になった。
- 以前の取得または後続処理が未完了のまま再開された。

- 取得成功または304から7日間を最新状態とする。
- 定期Workには最大24時間のflex期間を設定する。
- 前年より前または翌年より後の年を表示しただけでは、成功しない取得要求を繰り返さない。
- 将来年が取得範囲へ入った後の起動または定期更新で自動取得する。
- 祝日専用の手動更新ボタン、設定項目、専用画面を設けない。

## 7. WorkManagerと同時実行

- 定期更新と即時更新を固有名のユニークWorkとして管理する。
- アプリ更新や再起動で同じ定期Workを重複登録しない。
- 定期更新と即時更新が重なった場合も、ネットワーク要求は1件だけ実行する。
- RepositoryでもMutexなどを使用し、プロセス内の同時取得を防止する。
- 実行中に追加要求が発生した場合は、実行中処理の結果を共有する。
- 画面回転、バックグラウンド移行、一時的なプロセス再生成だけで重複処理を作らない。
- force stop中の取得は保証せず、解除後の次回起動時に状態を再確認する。

## 8. 再試行

### 8.1 再試行対象

- ネットワーク未接続、DNS、接続失敗
- タイムアウト、一時的なTLSまたは通信切断
- HTTP 408、429、5xx

### 8.2 方針

- 初回30分の指数バックオフを使用する。
- バックオフ上限は5時間とする。
- 1回の取得要求につき最大5回まで自動再試行する。
- 有効な`Retry-After`があればWorkManagerの許容範囲で考慮する。
- 失敗後15分間は、画面の再表示などによる新しい即時取得を開始しない。

### 8.3 即時再試行しないもの

- 408と429以外のHTTP 4xx
- JSON形式不正
- レスポンスサイズ超過
- 必須年不足
- 値または意味検証失敗

これらは既存キャッシュを維持し、次回の定期更新または後日のアプリ起動で再確認する。

## 9. HTTP応答

| 結果 | 処理 |
| --- | --- |
| 200 | 本文全体を検証し、成功した場合だけキャッシュ更新 |
| 304 | キャッシュを維持し、最終確認日時を更新 |
| 408、429、5xx | 既存キャッシュを維持して再試行 |
| その他4xx | 既存キャッシュを維持し、即時再試行しない |
| 通信・TLSエラー | 既存キャッシュを維持して再試行 |

HTTPステータスだけで既存キャッシュを削除しない。

## 10. JSON検証

### 10.1 構造

- UTF-8、BOMなしのJSONだけを許可する。
- ルートはJSONオブジェクトとする。
- キーは厳密な`yyyy-MM-dd`形式とする。
- 値は祝日名のJSON文字列とする。
- 重複キーを拒否する。
- 不正UTF-8、不正JSON、BOM、未知の値型を拒否する。

### 10.2 日付と名称

- 実在する日付だけを許可する。
- 空または空白だけの祝日名を拒否する。
- 祝日名は100文字以内とする。
- 不正な制御文字を拒否する。
- 有効な名称はAPIの表示名としてそのまま保存し、アプリ独自名称へ変換しない。

### 10.3 年の網羅性

- 日本時間で算出した前年、今年、翌年の各年に1件以上の祝日が必要である。
- 3年のいずれかが欠落または空なら、レスポンス全体を不完全として拒否する。
- 対象外の年が追加されていても、構造上有効ならレスポンス自体は拒否しない。
- 現行実装は対象外年を保存しない。
- レスポンス全体の検証完了前にRoomを変更しない。

## 11. 正規化と更新判定

- 年ごとに祝日を日付昇順へ並べる。
- 日付と祝日名から年単位の正規データを作る。
- 正規データのUTF-8バイト列からSHA-256を計算する。
- ハッシュは小文字64桁の16進数で保存する。
- 年単位ハッシュが一致する場合は内容変更なしとする。
- 祝日名だけの変更も内容変更とする。
- SHA-256は更新判定に使用し、API応答の真正性を保証するものではない。

## 12. Roomモデル

### 12.1 HolidayEntity

| 列 | 型 | 意味 |
| --- | --- | --- |
| date | ISO日付 | 主キー |
| year | 整数 | dateから算出した年 |
| name | 文字列 | 祝日名、1～100文字 |
| sourceId | 文字列コード | Holidays JPを表す安定コード |
| sourceDataHash | 文字列 | 対象年のSHA-256 |
| fetchedAt | Epochミリ秒 | 内容を取得した時点 |

`year`へインデックスを設定する。

### 12.2 HolidayFetchStateEntity

| 列 | 型 | 意味 |
| --- | --- | --- |
| year | 整数 | 主キー、対象年 |
| sourceId | 文字列コード | 取得元識別子 |
| availability | 文字列コード | `available`、`unavailable` |
| dataHash | 文字列またはnull | 年単位SHA-256 |
| fetchedAt | Epochミリ秒またはnull | 内容を最後に置換した時点 |
| lastCheckedAt | Epochミリ秒またはnull | 200または304で正常確認した時点 |
| lastAttemptedAt | Epochミリ秒またはnull | 最後の取得試行時点 |
| lastAttemptResult | 文字列コード | 成功、変更なし、通信失敗、HTTP失敗、検証失敗 |
| etag | 文字列またはnull | 条件付きリクエスト用 |
| lastModified | 文字列またはnull | 条件付きリクエスト用 |
| lastErrorCode | 文字列コードまたはnull | 分類済みエラー |

HTTPレスポンス全体に共通するETagとLast-Modifiedは、同じ取得で更新した3年へ同じ値を保存する。

## 13. トランザクション更新

1. レスポンス全体を検証する。
2. 3年分の正規データとハッシュを作る。
3. 変更された年と変更されていない年を決定する。
4. 1つのRoomトランザクションを開始する。
5. 変更年のHolidayEntityを取得結果で完全置換する。
6. APIから削除された祝日を対象年のキャッシュから削除する。
7. 変更の有無にかかわらず3年分の取得状態を更新する。
8. 更新世代と変更年を保存してコミットする。

- 途中失敗時は3年分すべてを更新前へ戻す。
- 変更のない年のHolidayEntityは書き換えない。
- 304ではHolidayEntityを書き換えない。
- 一度取得した対象範囲外の過去年キャッシュは自動削除しない。
- アプリデータ削除以外でキャッシュ全体を破棄しない。

## 14. キャッシュ状態モデル

年ごとに次を区別して公開する。

- 取得済み・最新
- 取得済み・更新期限超過
- 未取得
- 取得中
- 取得失敗・既存キャッシュあり
- 取得失敗・キャッシュなし
- APIの現在取得可能範囲外

- 取得済みキャッシュは7日を過ぎても利用可能とする。
- エラー状態とデータ利用可否を分離する。
- 取得失敗時に`available`な年を`unavailable`へ変更しない。

## 15. Repository公開モデル

共通Repositoryは少なくとも次を提供する。

- 指定日が祝日か
- 指定日の祝日名
- 指定年の祝日一覧
- 指定年の計算が確定か暫定か
- 複数年を含む期間を確定データだけで計算可能か
- 取得中、期限超過、失敗を含む年ごとの状態
- 最終確認日時
- 祝日データの更新世代と変更年

- RoomエンティティをUIや計算処理へ直接公開しない。
- 同一計算では祝日集合と取得状態の同じスナップショットを使用する。
- キャッシュは手動バックアップとAndroid自動バックアップへ含めない。

## 16. 受け入れ条件

1. Holidays JP APIから日本時間基準の3年分を取得できる。
2. HTTPS、タイムアウト、サイズ上限、条件付きリクエストを適用できる。
3. 不完全または不正なレスポンスで既存キャッシュを変更しない。
4. 3年分を1つのトランザクションで更新できる。
5. 年単位ハッシュで変更年だけを識別できる。
6. 304または同一内容でHolidayEntityを書き換えない。
7. 定期・即時要求を集約し、同時通信を防止できる。
8. 取得失敗後も利用可能な既存キャッシュを維持できる。
9. 未取得年と取得範囲外年を暫定状態として利用側へ通知できる。
10. 祝日キャッシュをバックアップ対象から除外できる。

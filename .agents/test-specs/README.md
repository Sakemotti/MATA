## 1. 目的

MATAの実装が、現時点で確定しているアプリ全体仕様と7画面の仕様を満たすことを、リリース単位で再現可能な形で確認する。

画面仕様の受け入れ条件227件を1件ずつテストIDへ対応付ける。加えて、画面仕様本文の詳細確認40件と、画面単体の受け入れ条件だけでは確認しにくい論理日、繰り返し、祝日、通知、ウィジェット、端末内保存、プライバシー、ビルド品質の横断確認136件を定義する。実行結果を記録する項目は合計403件とする。

初回リリース候補に対する実行証跡と残項目は[初回リリース試験棚卸し](initial-release-inventory.md)、403件の項目別結果は[リリース別試験結果の管理](results-management.md)、自動試験との1対1対応は[自動試験証跡TSV](automated-test-evidence.tsv)、担当は[初回リリース試験担当割り当て](closed-testing-assignments.md)、Closed testingの参加・端末・実施結果は[初回Closed testing実施台帳](closed-testing-log.md)へ記録する。テスターへの案内には[MATA Closed testing参加ガイド](closed-testing-tester-guide.md)を使用する。

## 2. 正とする文書

テスト項目と仕様が矛盾する場合は、次の順で扱う。

1. アプリ全体仕様と確定済み画面仕様を確認する。
2. 仕様間に矛盾がある場合は仕様を先に修正する。
3. 修正後の仕様に合わせて本項目書を更新する。

本項目書だけを根拠にプロダクト仕様を変更しない。

## 4. 項目の読み方

| 列 | 内容 |
| --- | --- |
| ID | 項目を一意に識別する固定ID。仕様変更で項目を削除する場合も別項目へIDを再利用しない |
| 優先度 | `P0`: 基本利用やデータ保全に必須、`P1`: リリース前に必須、`P2`: 補助的な表示・操作 |
| 推奨種別 | `UNIT`: ローカル単体、`INT`: DB・Repository・OS連携、`UI`: Compose UI、`E2E`: 主要フロー、`MANUAL`: 実機確認 |
| 条件・操作 | 必要な事前データ、端末状態、ユーザー操作 |
| 期待結果 | 合格と判断できる観測可能な結果 |
| 結果 | `未実施`、`合格`、`不合格`、`保留`、`対象外`のいずれか |
| 証跡・備考 | テスト日時、端末、ビルド、スクリーンショット、ログ、不具合IDなど |

`対象外`は安易に使用せず、対象外となるビルド・OS・端末条件と理由を証跡・備考へ記載する。

## 5. 基準テストデータ

実行時に現在日を `D0`、現在時刻を `T0`として置き換える。自動テストでは固定Clockを注入し、実機テストでは端末日時またはテスト専用データを使用する。

### 5.1 カテゴリ

| ID | 名前 | 用途 |

| `CAT-NONE` | カテゴリ未設定 | 固定区分 |

| `CAT-B` | ゲーム | 並び順・色・アイコン確認 |

### 5.2 TODO

最低限、次のTODOを用意する。

- 単発、毎日、平日のみ、曜日指定（平日・土日祝プリセットを含む）、毎月の指定日、毎月 第X X曜日（複数設定を含む）、月末、一定日数ごと、N週間にX回（2週間・1回・土日祝を含む）、月X回を各1件以上
- 期限なし、論理日境界より前の期限、境界と同時刻、境界より後の期限
- 説明なし、説明あり、タイトルと説明が表示上限を超えるもの
- 開始日前、実施期間中、終了済み、無期限
- 未完了、完了、スキップ、期限超過
- 通知なし、事前、期限時刻、期限後、複数通知、無効通知
- 履歴なし、大量履歴、現在期間の履歴あり、確定済み過去期間あり
- 通常、アーカイブ済み、完全削除確認用

### 5.3 外部状態

- 祝日情報: 取得成功、未取得、取得失敗、失敗後の取得成功

- バックアップ: 正常、旧対応形式、新しい未対応形式、破損、ハッシュ不一致、不正値、参照不整合、移行失敗

## 7. 実行順序

推奨順は次のとおり。

1. `UNIT`で論理日、繰り返し、期限、集計を確認する。
2. `INT`でDB、通知、バックアップ、広告同意状態を確認する。
3. 各画面の`UI`項目を確認する。
4. `E2E`で登録、実行、履歴、アーカイブ、復元、バックアップの主要フローを確認する。
5. `MANUAL`で実機OS連携、TalkBack、テーマ、最大フォント、Google Play、広告を確認する。
6. リリースゲートを実行する。

## 8. 主要E2Eシナリオ

| ID | シナリオ | 完了条件 |
| --- | --- | --- |
| `E2E-001` | 初回起動→カテゴリ追加→TODO追加→今日表示→完了→履歴確認 | 登録値、論理日、完了状態、カレンダー集計が一貫する |
| `E2E-002` | 共通終了時刻を変更して深夜帯を表示 | 全カテゴリが同じ対象論理日へ切り替わる |
| `E2E-003` | 週X回を複数日に完了→必要回数達成→期間結果確認 | 同日重複を防ぎ、達成後非表示、期間末結果が正しい |
| `E2E-004` | 平日のみTODO→祝日情報取得失敗→後日取得成功 | 暫定予定から現在・将来だけ再計算し、過去履歴を変えない |
| `E2E-005` | TODO編集→現在予定再計算→過去履歴確認 | 現在・将来だけ更新され、過去スナップショットを維持する |
| `E2E-006` | TODOをアーカイブ→詳細・履歴確認→現在期間内に復元 | アーカイブ期間を埋め戻さず、履歴を保持して残り回数を再計算する |
| `E2E-007` | アーカイブTODOを完全削除→カレンダー確認 | TODO、全履歴、期間結果、通知が消え、カレンダー集計も更新される |
| `E2E-008` | バックアップ作成→データ変更→復元 | 対象データが全置換され、通知と画面状態が再構成される |
| `E2E-009` | UMP同意状態変更→各広告表示箇所確認 | `canRequestAds`に従って広告だけが変化し、基本機能は制限されない |
| `E2E-010` | 通知とウィジェットからTODOを完了 | 一覧、履歴、ウィジェットが同じ完了状態へ更新される |

## 9. リリース判定

リリース可能とする最低条件は次のとおり。

- すべての`P0`と`P1`が合格している。
- `P2`の不合格は影響、回避策、対応時期が記録され、リリース判断者が承認している。
- 未解決のデータ消失、履歴改変、通知誤発火、広告同意違反がない。
- [app-core.md](app-core.md)の`REL`項目がすべて合格している。
- 不合格項目には再現手順、期待結果、実際結果、ログまたは画像、不具合IDが紐づいている。

## 10. 網羅性の保守

- 画面仕様へ受け入れ条件を追加した場合は、同じ番号のテストIDを対応する画面ファイルへ追加する。
- 受け入れ条件の意味を変更した場合は、対応テストの条件・操作と期待結果を同時に更新する。
- アプリ全体仕様の画面横断ルールを変更した場合は、`app-core.md`と関係する全画面ファイルを更新する。
- 実装技術の定数または方式を変更した場合は、関係する仕様と具体的な合否条件を同時に更新する。

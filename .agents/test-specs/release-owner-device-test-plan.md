## 1. 目的と対象

2026年9月7日時点で未実施のP0/P1かつ`RELEASE_OWNER`担当である262件を、同じ端末状態とテストデータを使い回せる19セッションへ分割する。Closed testing参加者へこの計画を割り当てず、`OWNER`が正式な公開判定の証跡を作るために使用する。

- セッション表は実施順と対象範囲を定める。個々の条件・操作・期待結果は各試験項目書を正とし、本書だけを見て合格にしない。
- 1回の操作で複数IDを確認してよいが、各IDが要求する条件を実際に観測した場合だけ項目別結果を更新する。
- Closed testingの署名済みRelease版を既定とする。失敗注入、応答順制御、低ストレージ等が必要な項目は、テスト専用データを持つDebug版またはエミュレータで確認する。
- 262件にはPlay Consoleやビルド確認も含まれる。`REL-010`は他の全P0/P1が確定した後だけ判定する。

## 2. 環境と証跡

実施前に次の環境へ匿名の識別名を付ける。実際に用意できない環境は、近い環境で代替済みにせず`未実施`または`保留`とする。

| 環境ID | 用途 | 必須条件 |

| `EMU-26` | minSdk・旧OS | API 26、スマートフォン幅 |

スクリーンショット、画面録画およびログの名前は`RO-<セッション>-<内容>-<YYYYMMDD>`とする。氏名、メールアドレス、参加URL、実際のTODO、通知内容およびアカウント画像を含めない。本番広告は表示だけを確認し、クリックしない。

## 3. 共通準備とデータ運用

1. `RO-01`が完了するまで、versionCode `1`で作成した更新確認データを削除・復元しない。
2. `1`から`2`への更新後、保持されたデータを記録して手動バックアップ`B0`を作る。
3. 各セッションのデータ名には`QA-ROxx-`を付け、実データと区別する。
4. 復元・アーカイブ・完全削除を含むセッションの直前に専用バックアップを作る。`B0`は上書きしない。
5. 端末日時、タイムゾーン、通知権限、正確なアラーム、テーマ、フォント、表示サイズ、ネットワークを変更した場合は、セッション終了時に元へ戻す。
6. 端末再起動や時刻待ちが必要な通知・ウィジェット項目は`RO-17`として早めに開始し、他セッションと並行して結果を待つ。

## 5. 推奨実行順

1. `RO-01`で上書き更新とデータ保持を確定し、`B0`を作る。
2. `RO-17`の将来通知と境界待ちを設定する。
3. `RO-02`〜`RO-09`で基本、TODO、カテゴリを確認する。
4. `RO-10`〜`RO-13`で履歴と破壊的操作を確認する。`RO-13`の直前に専用バックアップを作る。
5. `RO-14`〜`RO-16`で設定、バックアップ、UMPを確認する。`RO-15`には実データを使用しない。
6. 待機条件を満たした`RO-17`を完了する。
7. 各セッションで取得した表示証跡を利用しつつ、`RO-18`を全画面横断で実施する。
8. 未実施、保留、不具合およびConsole外部状態を解消してから`RO-19`を判定する。

## 7. 1セッションの実施手順

1. 対象version、環境ID、Android/API、端末形態、テーマ、フォント、権限、ネットワークおよび開始日時を記録する。
2. 対象IDの条件・操作・期待結果を元の項目書で確認する。
3. `QA-ROxx-`データだけで操作し、期待結果を観測する。破壊的操作前は対象データがテスト用であることを再確認する。
4. 合格条件を満たしたIDだけ、[項目別結果TSV](initial-release-results.tsv)へ`合格`と実行情報を記録する。
5. 不合格は画面、操作、期待値、実際値、再現率、端末、versionCodeおよび証跡を記録してIssue化する。該当IDは修正版の再試験まで`不合格`とする。
6. 正確な条件を作れなかったIDは`未実施`のままにするか、理由と解消条件を記録して`保留`とする。
7. [Closed testing実施台帳](closed-testing-log.md)へ`CT-*`実施行を追加し、次を実行する。

```powershell
node tools/test-specs/verify-results.mjs
node tools/test-specs/verify-assignments.mjs
node tools/test-specs/verify-automated-evidence.mjs
```

## 8. セッション完了条件

- 対象IDごとに`合格`、`不合格`、`保留`または根拠のある`対象外`が記録され、単なる一括の「問題なし」で代用していない。
- 実施日時、`OWNER`、versionCode、環境および証跡がTSVにある。
- 不合格がIssueと対応し、データ消失、履歴改変、通知誤発火または同意違反を放置していない。
- 個人情報、参加URL、秘密値、実データおよび本番広告クリックを証跡に含めていない。
- 3つの台帳検証コマンドが成功している。

`RO-19`を合格にできるのは、全P0/P1が合格し、Pre-launch report、Closed testing要件、ポリシー、Data safety、SDKおよび本番公開判断の外部ゲートが揃った場合だけである。

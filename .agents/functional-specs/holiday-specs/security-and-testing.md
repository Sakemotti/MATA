# MATA 祝日データ安全性・テスト仕様

- 文書状態: 初版
- 最終更新日: 2026-08-10

## 1. 信頼境界

Holidays JP APIの応答は外部入力として扱い、通信成功だけでは信頼しない。

- TLS、HTTP状態、展開後サイズ、文字コード、JSON構造、値、年の網羅性を検証する。
- レスポンス全体の検証成功前に既存キャッシュを変更しない。
- 外部値をSQL、ログ書式、ファイル名、通知識別子として直接使用しない。
- 祝日名は画面表示時に通常のCompose Textとして扱い、HTMLとして解釈しない。

## 2. プライバシー

- APIへTODO、カテゴリ、履歴、設定、通知内容を送信しない。
- 広告ID、Android ID、インストールID、端末モデルを追加送信しない。
- 認証、ユーザーアカウント、Cookieを使用しない。
- 祝日データ取得のためHolidays JPへ通信することをプライバシーポリシーへ記載する。
- 祝日取得だけを目的とした解析イベントや利用状況送信を追加しない。

## 3. ログ

- APIレスポンス本文をログへ出力しない。
- 祝日名を通常ログへ出力しない。
- TODOなどのユーザーデータを取得処理のログへ関連付けない。
- ログには対象年、HTTP結果分類、処理段階、エラーコード、変更有無、試行回数だけを記録できる。
- ETag、Last-Modified、レスポンスハッシュを通常ログへ出力しない。
- 技術的例外をユーザー向けメッセージへそのまま表示しない。

## 4. 保存とバックアップ

- HolidayEntityとHolidayFetchStateEntityはアプリ専用Roomデータベースへ保存する。
- 祝日キャッシュを手動バックアップへ含めない。
- Android自動バックアップへ含めない。
- キャッシュファイルやHTTP一時ファイルをアプリ専用領域外へ作成しない。
- 一時レスポンスがある場合は成功、失敗、プロセス再開後に削除する。

## 5. データ移行

- HolidayEntityとHolidayFetchStateEntityをRoomスキーマ管理対象とする。
- すべてのスキーマ変更にマイグレーションと移行テストを用意する。
- destructive migrationを通常の更新手段として使用しない。
- キャッシュだけを移行できない場合は、TODOなどのユーザーデータへ影響させず、祝日キャッシュを再取得可能な未取得状態へ移行する。
- データソース、日付形式、名称の意味、正規化方法、ハッシュ方式を変更する場合は取得元またはキャッシュ形式のバージョンを更新する。
- 公開済みの履歴を祝日キャッシュ移行で再計算しない。

## 6. 単体テスト: HTTP

- HTTP 200、304
- HTTP 408、429、その他4xx、5xx
- `Retry-After`あり・なし
- 接続拒否、DNS失敗、通信切断
- 接続タイムアウト、読み取りタイムアウト
- TLS失敗
- HTTPSリダイレクト
- HTTPへのダウングレードリダイレクト
- リダイレクト上限超過
- Content-Length既知・未知
- gzip圧縮
- 展開後1 MiBちょうど・超過
- ETagだけ、Last-Modifiedだけ、両方、どちらもなし
- 必要キャッシュが揃った条件付きリクエスト
- キャッシュ不足状態で受けた304と無条件再取得

## 7. 単体テスト: JSONと検証

- 正常な3年分JSON
- 日付順が不規則なJSON
- 祝日名に日本語、空白、記号を含むJSON
- うるう年と2月29日
- 振替休日と国民の休日
- 重複キー
- 不正日付、存在しない日付、日付形式違反
- 空文字、空白だけ、100文字、101文字の祝日名
- 不正な制御文字
- 不正UTF-8、BOM付きJSON
- 不正JSON、ルート配列、非文字列の値
- 前年、今年、翌年の各欠落または空
- 対象外年の追加
- レスポンス全体の検証失敗で既存データが変わらないこと

## 8. 単体テスト: 正規化と保存

- 同じデータを異なる順序で受信しても同じ年単位ハッシュになる。
- 祝日の追加、削除、日付変更、名称変更でハッシュが変わる。
- 同一ハッシュではHolidayEntityを書き換えない。
- 304でHolidayEntityを書き換えず、lastCheckedAtだけを更新する。
- APIから削除された祝日を対象年のキャッシュから削除する。
- 3年分の途中保存失敗で全体をロールバックする。
- 取得済み過去年を対象範囲外になったことだけで削除しない。
- availabilityと最後の試行結果を独立して保持する。

## 9. 単体テスト: 取得制御

- 初回起動時の未取得判定
- 7日未満と7日経過後の更新判定
- 日本時間の12月31日と1月1日の対象年
- 端末タイムゾーンと日本時間の年が異なる場合
- 取得範囲外の年で不要な通信を行わないこと
- 定期Workの重複登録防止
- 定期更新と即時更新の集約
- 複数画面からの同時要求
- 30分開始の指数バックオフ
- 5時間のバックオフ上限
- 最大5回の試行
- 失敗後15分の即時取得抑止
- force stop解除後の状態再確認

## 10. 単体テスト: 繰り返し計算

- 取得済み祝日を平日のみTODOから除外する。
- 振替休日と国民の休日を除外する。
- 土日をキャッシュ状態にかかわらず除外する。
- 曜日指定、毎日、月指定、一定日数ごと、週X回、月X回を祝日で除外しない。
- 未取得年を月曜日から金曜日で暫定計算する。
- 期限超過キャッシュを利用して計算する。
- 取得失敗時に既存キャッシュを利用する。
- 複数年の一部だけ未取得の場合に範囲全体を暫定と識別する。
- 無期限TODOを無制限に展開しない。

## 11. 統合テスト: 更新反映

- 初回起動で3年分を取得する。
- 7日未満では不要な再取得を行わない。
- 7日経過後に条件付きリクエストを行う。
- 変更年だけを後続処理へ通知する。
- 現在日に祝日が追加された場合、未操作TODOを一覧とウィジェットから除外する。
- 現在日の祝日が削除された場合、該当TODOを表示する。
- 完了またはスキップ済みの現在日記録を維持する。
- 過去の完了、スキップ、未完了、期間結果を変更しない。
- 祝日名だけの変更を現在と将来の表示へ反映する。
- 古い将来通知を取り消し、新しい通知を登録する。
- 経過済み通知を発火させない。
- 古いアラームをReceiverの再検証で抑止する。
- 全ウィジェットを更新する。

## 12. 統合テスト: 障害復旧

次の各段階で失敗またはプロセス終了を注入する。

- HTTP接続前、読み取り中、読み取り完了後
- JSON検証中
- Roomトランザクション開始前、更新中、コミット後
- 更新世代保存後
- ドメイン再計算中
- 通知取消・再登録中
- ウィジェット更新中

各ケースで次を確認する。

- キャッシュ更新前なら以前のキャッシュを維持する。
- Room更新途中なら3年分をロールバックする。
- コミット後なら同じ更新世代から後続処理を再開する。
- 再開を複数回実行しても履歴、通知、ウィジェットを重複させない。
- 後続処理の失敗で正常な祝日キャッシュを元へ戻さない。
- 暫定状態でもTODOの保存と表示を継続できる。

## 13. バックアップ連携テスト

- 手動バックアップにHolidayEntityを含めない。
- 手動バックアップにHolidayFetchStateEntityを含めない。
- 復元前の端末にある有効な祝日キャッシュを維持する。
- 復元TODOに必要な年が不足する場合は取得Workを登録する。
- 取得完了まで暫定計算する。
- 取得後に未確定の現在と将来だけを更新する。
- 確定済みの復元履歴を変更しない。

## 14. UI・アクセシビリティテスト

- 取得済み、期限超過、未取得、取得中、取得失敗、範囲外を区別できる。
- TODO編集画面に暫定表示の理由を表示できる。
- 祝日取得失敗がTODO保存を妨げない。
- 祝日として除外した日付と名称をプレビューできる。
- 一覧とカレンダーで暫定状態を識別できる。
- ウィジェットで必要な警告とアプリ起動操作を利用できる。
- 祝日取得失敗のシステム通知を表示しない。
- TalkBackで取得状態、暫定理由、祝日名を読み上げられる。
- フォント拡大時も警告と主要情報が欠けない。

## 15. CIと外部API契約確認

- 通常のCIは実際のHolidays JP APIへ接続しない。
- MockWebServerなどでHTTP応答を再現する。
- Clock、対象年、ZoneId、ネットワーク状態をテストから注入可能にする。
- 正常、不正、境界値を含むゴールデンJSONをリポジトリへ保存する。
- 外部APIの形式確認は任意の定期監視として分離する。
- 外部API障害を理由に通常のPull Requestテストを失敗させない。
- API形式変更を検出した場合は、既存キャッシュを維持したまま取得失敗として扱う。

## 16. 受け入れ条件

1. 外部応答を厳密に検証し、不正データでキャッシュを変更しない。
2. 祝日取得通信へユーザーデータや端末識別子を含めない。
3. API本文と祝日名を通常ログへ出力しない。
4. Roomスキーマ変更をユーザーデータへ影響させず移行できる。
5. HTTP、JSON、年境界、同時実行、再試行を自動テストできる。
6. すべての繰り返し方式で祝日の適用範囲を検証できる。
7. 更新後の画面、通知、ウィジェット連携を統合テストできる。
8. 各処理段階の失敗とプロセス終了から一貫した状態へ回復できる。
9. バックアップ対象外と復元後の再取得を検証できる。
10. 通常CIを外部APIの可用性から独立させられる。

# MATA 手動バックアップ作成仕様

- 文書状態: 初版
- 最終更新日: 2026-08-10

## 1. 開始経路

- 設定画面の「バックアップを作成」から開始する。
- 開始前に、TODO、説明、履歴などの個人情報を含む可能性があることを表示する。
- アプリ独自の暗号化を行わないことと、安全な保存先を選んでファイルを適切に管理する必要があることを案内する。
- ユーザーが案内を確認した後に保存先選択を開く。

## 2. 保存先選択

- Storage Access Frameworkの`ACTION_CREATE_DOCUMENT`を使用する。
- MIMEタイプは`application/zip`とする。
- ストレージ全体への読み書き権限を要求しない。
- 保存先と最終ファイル名はユーザーが選択する。
- 初期ファイル名は`MATA_backup_yyyyMMdd_HHmmss.mata-backup`とする。
- ファイル名の日時には選択画面を開く時点の端末ローカル日時を使用する。
- ユーザーがファイル選択をキャンセルした場合はエラーを表示せず設定画面へ戻る。
- DocumentProviderによる同名ファイルの確認、置換、別名化の挙動に従う。アプリが独自に既存ファイルを探索して上書きしない。

取得したURIは処理中だけ永続化可能な権限として保持する。バックアップの成功、失敗、または未完了処理の後始末が完了した時点で権限を解放し、URIを長期履歴として保存しない。

## 3. 排他制御

- 保存先決定後から後始末完了まで、バックアップ用のアプリ内排他ロックを取得する。
- 同時に実行できるバックアップまたは復元は1件だけとする。
- 処理中はTODO、カテゴリ、履歴、対象設定を変更する操作を無効にする。
- 通知、ウィジェット、整合処理などから発生するデータ変更も同じロックまたはRepositoryの調停機構で待機させる。
- ロック取得前に重複操作が行われた場合は新しい処理を開始せず、進行中の処理状態を表示する。

## 4. 整合スナップショット

### 4.1 固定する値

1回のバックアップでは次を同じ作成時点へ固定する。

- Roomのカテゴリ、TODO、通知設定、実行記録、期間結果、実行状態
- DataStoreのバックアップ対象設定
- バックアップ作成時点
- アプリバージョン名とコード
- Roomスキーマバージョン

Room読み取り中に行ごとに異なる時点が混在しないよう、読み取りトランザクションまたは同等の一貫スナップショットを使用する。DataStore値は排他ロック取得後に1回だけ取得し、処理中に取り直さない。

### 4.2 件数と順序

- 各配列を[形式仕様](format-v1.md)の正規順序で読み出す。
- 件数はスナップショットと同じ読み取り境界から取得する。
- 出力中に件数、非圧縮バイト数、SHA-256を同時に計算する。
- 件数または出力結果がスナップショットと一致しない場合は成功させない。

## 5. 出力処理

処理順は次のとおり。

1. 処理IDと出力URIをアプリ専用領域の操作ジャーナルへ保存する。
2. DocumentProviderの出力ストリームとZIPストリームを開く。
3. `data.json`エントリを開始する。
4. UTF-8 JSONをレコード単位でストリーミング出力する。
5. 非圧縮バイト列のSHA-256、バイト数、件数を確定する。
6. `data.json`を閉じる。
7. 確定した値から`manifest.json`を生成して書く。
8. ZIPをfinishしてすべてのストリームを閉じる。
9. 出力ファイルを読み直し、ZIP終端、必須エントリ、CRC、manifest、SHA-256を検証する。
10. 検証成功後に操作ジャーナルを成功へ更新する。

- 全レコードまたは`data.json`全体を一度にメモリへ保持しない。
- JSON生成、ダイジェスト計算、ZIP出力の各ストリームは順に連結する。
- タイトル、説明、保存先URI、バックアップ内容をログへ出力しない。
- `manifest.json`を書き終える前または最終検証前のファイルは不完全とみなし、成功として扱わない。

## 6. 長時間処理

- 固有名のユニークな`CoroutineWorker`で実行する。
- 通常は迅速な処理として開始し、Androidの要件を満たす範囲でexpedited workを利用できる。
- 数分を超える可能性がある場合は長時間実行Workerへ移行し、必要なフォアグラウンド通知を表示する。
- 画面回転、構成変更、設定画面からの離脱、アプリのバックグラウンド移行だけでは中断しない。
- UIは処理IDからWorkManagerと操作ジャーナルの状態を再購読し、プロセス再生成後も進捗表示へ戻る。
- WorkManagerから停止要求を受けた場合は協調的に停止し、ストリームを閉じて失敗時の後始末へ移る。
- OSによる強制終了で処理を継続できなかった場合は、次回起動時に操作ジャーナルから未完了処理を検出する。

## 7. 進捗表示

- 保存先決定後は、ユーザー操作ではキャンセルできない進捗ダイアログを表示する。
- 件数または処理バイト数から妥当な進捗率を算出できる場合は確定的な進捗を表示する。
- 算出できない段階では不確定の進捗を表示する。
- 少なくとも「準備中」「データを書き出しています」「ファイルを検証しています」の段階を区別する。
- 進捗開始、成功、失敗を支援技術へ通知する。

## 8. 成功

- 最終検証、ストリームのclose、ジャーナル更新がすべて成功した時点で完了とする。
- URI権限とアプリ専用の一時情報を解放する。
- 排他ロックを解放する。
- 設定画面へ「バックアップを作成しました」と表示する。
- バックアップ保存先URIをアプリ内の履歴や最近使った場所として保持しない。

## 9. 失敗

- 書き込み不能、容量不足、DocumentProvider切断、アクセス権喪失、整合スナップショット失敗、ZIP生成失敗、最終検証失敗を区別可能な内部エラーとして扱う。
- ユーザーには原因に応じた簡潔なメッセージと再試行可能性を表示する。
- 設定画面に留まり、端末内の元データを変更しない。
- 出力URIに対して不完全ファイルの削除を試みる。
- DocumentProviderが削除を許可しない、または削除確認ができない場合は、選択した保存先に不完全なファイルが残る可能性を案内する。
- 不完全ファイルは有効な`manifest.json`と最終検証済み状態を持たないため、復元処理では拒否する。
- ストリーム、一時情報、URI権限、排他ロックを必ず解放する。

## 10. 強制終了後の回復

起動時に未完了の作成ジャーナルを検出した場合は次を行う。

1. 該当Workerが現在実行中か確認する。
2. 実行中なら状態購読を再開する。
3. 実行中でなければ出力ファイルを不完全として削除を試みる。
4. 削除できなければユーザーへ残存可能性を案内する。
5. URI権限、一時情報、排他状態、ジャーナルを解放する。

自動的に新しいバックアップ作成を再開しない。ユーザーが設定画面から改めて開始する。

## 11. 受け入れ条件

1. SAFから任意の対応DocumentProviderへ保存できる。
2. 選択キャンセルをエラーとして表示しない。
3. RoomとDataStoreから同じ処理時点の整合データを出力できる。
4. 大規模データを全件メモリへ保持せず出力できる。
5. manifestをdataのハッシュと件数確定後に生成できる。
6. 出力完了後に作成したファイルを読み直して検証できる。
7. 作成中のデータ変更とバックアップ・復元の重複実行を防止できる。
8. 画面回転、バックグラウンド移行、プロセス再生成後に処理状態を表示できる。
9. 失敗または強制終了後に不完全ファイルの削除を試みられる。
10. 個人情報、URI、バックアップ内容をログや長期内部履歴へ残さない。

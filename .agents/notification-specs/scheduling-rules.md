# MATA 通知スケジュール仕様

- 文書状態: 初版
- 最終更新日: 2026-08-10
- 対応する決定事項: 通知質問 6～12、27～56、84～90

## 1. 目的

TODOごとの通知設定を、ドメイン仕様で算出された実行日と期限へ適用し、Androidへ登録する規則を定義する。

通知スケジューラは曜日、繰り返し、論理日、回数達成を独自に判定しない。[繰り返し計算仕様](../domain-specs/recurrence-rules.md)の計算結果を入力とする。

## 2. 通知タイミング

### 2.1 種別

| 種別 | relation | 入力 |
| --- | --- | --- |
| 期限より前 | before | 1～999と単位 |
| 期限時刻ちょうど | at | 差なし |
| 期限より後 | after | 1～999と単位 |

beforeとafterの単位はminute、hour、dayから選択する。atはamountを0とし、単位を持たない。

### 2.2 分と時間

- minuteは期限時点から実時間で指定分を加減算する。
- hourは期限時点から実時間で指定時間を加減算する。

### 2.3 日

dayは24時間固定のDurationではなく、端末タイムゾーン上の期限のローカル日付を指定日数だけ移動し、同じローカル時刻を使用する。

夏時間で移動先時刻が存在しない場合と重複する場合は、ドメイン仕様のZoneId解決規則を使用する。

### 2.4 重複

同じrelationで名目上の差が同じ設定を重複登録できない。

- 1日は重複判定上1440分として扱う。
- 1日前と24時間前は重複とする。
- 60分前と1時間前は重複とする。
- beforeとafterは差が同じでも別設定とする。

TODO編集画面では実際の発火順に自動整列して表示する。

## 3. 候補時点

対象論理日、期限時点、通知タイミングから候補時点を算出する。

    before: 期限時点 - 差
    at:     期限時点
    after:  期限時点 + 差

### 3.1 事前通知

- 対象論理日の開始より前になることを許可する。
- 最初の実行日の候補がTODO作成時点以前なら、その候補だけを登録しない。
- startDateより前のカレンダー日に候補があっても、TODO保存後の将来時点なら登録できる。
- 事前通知には対象論理日を含め、どの日のTODOか識別可能にする。

### 3.2 期限超過通知

- 候補時点が論理日終了より前なら有効。
- 候補時点が論理日終了以後なら無効。
- 無効な通知設定は削除せず、発火対象外として保持する。
- TODO、カテゴリ、共通終了時刻の変更で無効になる場合は、保存前に件数と理由を表示する。

### 3.3 経過済み候補

登録処理時点以前の候補をOSへ登録せず、即時発火もさせない。次の有効候補を探索する。

## 4. 論理日終了と同時の通知

期限時点が論理日終了と同じ場合のat通知は、終了境界通知として扱う。

- 表示文言は「この日の期限になりました」とする。
- 予定時刻から5分以内に受信した場合だけ表示する。
- 表示前に通常TODOの未完了または回数指定TODOの期間状態を確定する。
- 有効期間終了後のため完了アクションを表示しない。
- 5分を超えて遅延した場合は表示せず失効させる。

終了境界より後になるafter設定は無効である。

## 5. 次回候補方式

### 5.1 登録数

将来分を大量に事前登録しない。1つのTodoNotificationEntityにつき、次に発火する有効候補を最大1件だけOSへ登録する。

OSへの最大登録数は、現在有効な通知タイミング設定数となる。

### 5.2 次回探索

次回候補探索は繰り返し方式ごとの次回実行日計算を使用する。無期限TODOを1日ずつ無制限に走査しない。

探索を終了する条件:

- 将来の有効候補が見つかった。
- endDateを超えた。
- TODOが終了済みまたはアーカイブ済み。
- 通知設定が現在の期限・終了時刻では常に無効。

### 5.3 発火後

候補が次のいずれかになった後、同じ通知設定の次回候補を計算する。

- 通知を表示した。
- 最新状態の再検証で失効した。
- TODOが完了またはスキップ済みだった。
- ユーザーが通知を消去または開いた。

## 6. 週X回・月X回

- 現在期間が未達成なら、各論理日について期限と通知候補を算出する。
- 同一論理日に完了またはスキップ済みなら、その日の候補を登録しない。
- 必要回数へ到達したら、現在期間の残りアラームを取り消す。
- 完了取り消しで未達成へ戻った場合は、現在時刻より後の候補だけを再登録する。
- 次の期間では新しい期間境界と進捗から候補を算出する。

## 7. AlarmManager

### 7.1 共通

- 繰り返しアラームAPIを使用しない。
- すべて1回限りのRTC_WAKEUPアラームとして登録する。
- PendingIntentは明示的、変更不可能とする。
- OS登録前に通知権限、通知チャンネル、TODO状態を検証する。

### 7.2 正確な方式

SCHEDULE_EXACT_ALARMが許可され、canScheduleExactAlarmsがtrueの場合はsetExactAndAllowWhileIdleを使用する。

- 正確なアラーム登録直前にも許可状態を確認する。
- SecurityExceptionなどの権限エラーではクラッシュさせない。
- 権限エラー時は通常方式へフォールバックする。

### 7.3 通常方式

正確なアラームを使用できない場合はsetAndAllowWhileIdleを使用する。

- 指定時刻より遅れる可能性がある。
- 受信時点で期限状態と論理日終了を再検証する。
- 論理日終了後に届いた候補は、終了境界通知の5分以内という例外を除き表示しない。

### 7.4 権限がない場合

次の場合は通知設定を保持しつつ、AlarmManagerへ登録しない。

- POST_NOTIFICATIONSが必要な端末で未許可
- アプリ全体の通知が無効
- todo_reminders_v1チャンネルが無効

許可または有効化を検出した時点で、経過済み候補を除いて再登録する。

## 8. 候補キーとrequestCode

候補キーは少なくとも次から生成する。

- TODO ID
- 通知設定ID
- 対象論理日
- TODO定義リビジョン

requestCodeは内部テーブルで永続管理し、候補キーと一意に対応させる。単純なハッシュ値だけに依存せず、衝突を検出した場合は未使用値を割り当てる。

編集によって定義リビジョンが変わった場合、旧リビジョンのPendingIntentを取り消してから新しい候補を登録する。

## 9. ScheduledNotificationEntity

OS登録状況を追跡する内部テーブルを設ける。

| 列 | 意味 |
| --- | --- |
| candidateKey | 主キー |
| todoId | 対象TODO |
| notificationSettingId | 通知設定 |
| logicalDate | 対象論理日 |
| definitionRevision | 対象定義 |
| triggerAt | UTCの予定時点 |
| requestCode | PendingIntent識別子、一意 |
| schedulingMode | exactまたはinexact |
| state | pending、scheduled、delivered、suppressed、canceled、failed |
| failureCode | 失敗理由、なければnull |
| createdAt | 作成時点 |
| updatedAt | 更新時点 |

このテーブルは再生成可能な内部情報であり、手動バックアップとユーザー履歴には含めない。再登録に不要となった完了レコードは、実装時に定める保守期間後に削除する。

## 10. アラーム受信時の再検証

通知を表示する前に、端末内データから次を再取得する。

- TODOが存在すること
- アーカイブされていないこと
- 通知設定が存在すること
- 定義リビジョンが一致すること
- 対象論理日が現在も有効であること
- 完了またはスキップ済みではないこと
- 回数指定TODOが未達成であること
- 通知権限とチャンネルが有効であること

結果:

- 編集、削除、アーカイブ済みの古い候補は表示せずsuppressedとする。
- 別経路で完了済みなら表示せず次回候補を計算する。
- 期限後だが論理日終了前なら、本文を期限超過状態へ変更する。
- 論理日終了後なら、終了境界通知の例外を除き表示しない。
- force stop後の復帰では、経過済み候補を表示しない。

Receiver内で祝日取得などのネットワーク通信を行わない。端末内キャッシュと保存済み状態だけを使用する。

## 11. 受け入れ条件

1. 期限前、期限時刻、期限超過の複数設定から正しい候補を算出できる。
2. 分、時間、カレンダー日の差をタイムゾーン込みで扱える。
3. 論理日終了後の無効な通知を表示しない。
4. 通知設定1件につき次回候補だけをOSへ登録できる。
5. 正確な方式と通常方式を許可状態に応じて切り替えられる。
6. 編集後の古いPendingIntentが誤通知を表示しない。
7. 無期限TODOの次回候補を無制限走査なしで算出できる。
8. 回数指定TODOの達成・取り消しに応じて登録を更新できる。

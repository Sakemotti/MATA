# MATA 繰り返し計算仕様

- 文書状態: 初版
- 最終更新日: 2026-08-10
- 対応する決定事項: 繰り返し計算質問 19～66、127～136、146～152

## 1. 目的

TODO一覧、カレンダー、通知、ウィジェットが同一の結果を得られるように、論理日、実行対象、期限、週X回・月X回の進捗を算出する規則を定義する。

繰り返し計算はAndroid API、Room、DataStoreへ依存しない純粋なKotlinのドメイン処理とする。同じ入力には常に同じ結果を返し、計算中にデータを保存または変更しない。

## 2. 計算入力

計算処理は少なくとも次を明示的な入力として受け取る。

- TODO定義
- 対象カテゴリまたはカテゴリ未設定の終了時刻
- 現在時刻を提供するClock
- 端末のZoneId
- 週の開始曜日
- 祝日情報と取得状態
- 保存済み実行記録
- 保存済み期間結果
- 計算対象の日付範囲

システム時刻、端末設定、データベースを計算処理内から直接参照しない。

## 3. 論理日

### 3.1 境界

一日の終了時刻を同時に次の論理日の開始時刻とする。

論理日Dの範囲は、端末タイムゾーン上で次の半開区間となる。

    Dの終了時刻以上の開始時点
    以上
    Dの翌日の終了時刻
    未満

例として終了時刻が4:00の場合、8月10日4:00以上8月11日4:00未満を8月10日分とする。

現在のローカル時刻が終了時刻より前ならカレンダー日の前日、終了時刻以後なら同じカレンダー日を論理日とする。終了時刻が0:00の場合は通常のカレンダー日と一致する。

### 3.2 適用する終了時刻

- categoryIdがあるTODOは、そのカテゴリのendHourを使用する。
- categoryIdがnullのTODOは、DataStoreの共通終了時刻を使用する。
- 確定済み履歴はsnapshotJsonに保存された当時の終了時刻を使用する。

### 3.3 タイムゾーンと夏時間

- 現在と将来の算出には端末の現在ZoneIdを使用する。
- タイムゾーン変更後も確定済み履歴のlogicalDateは変更しない。
- 夏時間により存在しないローカル時刻は、ZoneIdの規則に従って直後の有効時刻へ進める。
- 夏時間により時刻が重複する場合は、先に到来するオフセットを使用する。

## 4. 有効期間

- startDateは実行対象に含む。
- endDateも実行対象に含む。
- endDateがnullの場合は無期限とする。
- 対象論理日がstartDateより前、またはendDateより後なら実行対象外とする。
- アーカイブ済みTODOは現在と将来の実行対象外とする。

## 5. 通常の繰り返し

### 5.1 繰り返しなし

startDateだけを実行対象とする。endDateはstartDateと同じであるものとして検証する。

### 5.2 毎日

有効期間内のすべての論理日を実行対象とする。

### 5.3 平日のみ

月曜日から金曜日のうち、日本の祝日ではない論理日を実行対象とする。

- Holidays JPから取得済みの祝日、振替休日、国民の休日を除外する。
- 対象年の祝日を取得できていない場合は、月曜日から金曜日を暫定的な実行日とする。
- 取得済みキャッシュがある場合は、通信失敗時もキャッシュを優先する。
- 後から祝日を取得した場合は、未確定の現在と将来だけを再計算する。
- 確定済み履歴は祝日取得後も変更しない。

祝日キャッシュは年単位で、取得日時と取得元データの識別情報を保存する。祝日再計算に失敗した場合は既存結果を維持し、次回再試行する。

取得、暫定状態、更新後の再計算は[日本の祝日データ仕様](../holiday-specs/README.md)に従う。

### 5.4 曜日指定

- 月曜日から日曜日までのうち、1つ以上の曜日を選択する。
- 対象論理日の曜日が選択集合に含まれる場合に実行対象とする。
- 祝日であることを理由に除外しない。

### 5.5 毎月の指定日

- 1～31の指定日を1つ持つ。
- その月に指定日が存在する場合は指定日を使用する。
- 指定日が存在しない月は、その月の最終日を使用する。
- startDateとendDateによる有効期間判定を最後に適用する。

例として31日指定は、2月には2月末日、4月には4月30日を実行日とする。

### 5.6 毎月 第X X曜日

- 第1～第5と月曜日～日曜日の組み合わせを1つ以上持つ。
- 組み合わせは複数選択でき、同一の組み合わせを重複して保持しない。
- 対象論理日の月内序数を`((日 - 1) / 7) + 1`で求め、曜日と月内序数の組み合わせが選択集合に含まれる場合に実行対象とする。
- 例として「第1月曜日」と「第3金曜日」を選択した場合は、各月の両方の日を実行対象とする。
- 第5曜日が存在しない月はその組み合わせの実行日を生成せず、月末や翌月へ振り替えない。
- startDateとendDateによる有効期間判定を最後に適用する。
- 祝日であることを理由に除外しない。

### 5.7 毎月の月末

各月の最終論理日を実行対象とする。うるう年の2月29日を含め、YearMonthの長さから算出する。

### 5.8 一定日数ごと

- 間隔Nは1以上の整数とする。
- startDateを1回目の実行日とする。
- 対象論理日とstartDateの経過日数がNの倍数なら実行対象とする。
- 実際の完了日時、スキップ、未完了によって次回基準を変更しない。

## 6. 期限

### 6.1 期限未設定

論理日の終了時点を期限とする。

### 6.2 明示的な期限

論理日D、終了時刻C、期限時刻Tに対し、期限は論理日の開始後に最初に到来するTとする。ただしTがCと同じ場合は論理日の終了時点とする。

- TがCより後なら、Dと同じカレンダー日のT。
- TがC以前なら、Dの翌カレンダー日のT。

例:

- 終了4:00、8月10日分、期限23:00 → 8月10日23:00
- 終了4:00、8月10日分、期限2:00 → 8月11日2:00
- 終了4:00、8月10日分、期限4:00 → 8月11日4:00
- 終了0:00、8月10日分、期限0:00 → 8月11日0:00

### 6.3 期限超過

- 現在時刻が期限を過ぎ、実行記録がなく、論理日終了前なら期限超過とする。
- 期限超過は保存状態ではなく計算結果とする。
- 論理日終了時に未操作なら、通常TODOは確定済み未完了へ遷移する。
- 未完了を次回へ繰り越さない。

## 7. 週X回

### 7.1 設定

- 必要回数Xは1～7。
- 期間は設定された週の開始曜日から連続する7論理日。
- TODOのstartDateまたはendDateが期間途中にある場合は、有効期間との積集合を部分期間とする。

### 7.2 部分期間

- 部分期間でも必要回数Xを減らさない。
- 有効日数がX未満の場合は登録・編集時に達成不能の警告を表示する。
- 警告後の保存は許可する。

### 7.3 表示と進捗

- 未達成の間は、部分期間内の各論理日に今日のTODOとして表示する。
- 同一論理日に完了またはスキップ済みなら、その日は再表示しない。
- 同一論理日の完了は1回まで。
- 完了数がX以上になった時点で、その期間の残り日には表示せず通知もしない。
- 完了取り消しによりX未満へ戻った場合、現在期間内なら表示と将来通知を再開する。
- 進捗は実際の完了数と必要回数を表示する。編集により完了数が必要回数を超えた場合は5/3回のような表示を許可する。

## 8. 月X回

### 8.1 設定

- 必要回数Xは1～31。
- 期間は各月の1日から月末まで。
- TODOのstartDateまたはendDateが月途中にある場合は、有効期間との積集合を部分期間とする。

部分期間、表示、同日制限、達成後の非表示、取り消し後の再表示は週X回と同じ規則を使用する。

## 9. 回数指定TODOの記録

### 9.1 完了

- 1論理日につき1回だけ完了できる。
- 完了日はTodoExecutionEntityへcompletedとして保存する。
- 必要回数へ達した後は追加完了できない。
- 設定編集前に必要回数を超える完了が存在していた場合は削除しない。

### 9.2 スキップ

- スキップした論理日だけ非表示にする。
- スキップ記録をTodoExecutionEntityへ保存する。
- 必要回数と残り回数を減らさない。
- スキップの取り消しを提供しない。
- スキップした論理日に同じTODOを完了できない。

### 9.3 未操作

何も操作しなかった日について日単位の未完了記録を生成しない。

### 9.4 期間結果

期間結果は、自然な期間末とTODOのendDateのうち早い方の論理日終了時に確定する。

期間結果には次を保存する。

- 有効な期間開始日と終了日
- 必要回数
- 実際の完了回数
- 達成または未達成
- 確定日時
- TODO、カテゴリ、終了時刻、週開始曜日などのスナップショット

カレンダーでは有効な期間最終日に表示する。スキップは必要回数を減らさず、完了数にも含めない。

アーカイブ時は進行中期間を確定せず、既存の完了・スキップ記録だけを保持する。

## 10. 設定変更時の期間

週の開始曜日を変更した場合:

- 確定済み期間結果を変更しない。
- 現在と将来の週境界を新しい開始曜日で再計算する。
- 保存済み実行記録のlogicalDateを新しい期間境界へ当てはめ、現在期間の完了数を数え直す。

必要回数を変更した場合:

- 必要回数を減らして完了数以上になれば、現在期間を達成済みとして扱う。
- 必要回数を増やして完了数未満になれば、現在期間内で表示と通知を再開する。
- 保存済みの完了・スキップ記録を削除しない。

## 11. 計算エンジン

### 11.1 責務

計算エンジンは次を個別に提供する。

- 指定時点の論理日
- 論理日の開始・終了時点
- 指定論理日が実行対象か
- 日付範囲内の実行対象
- 期限時点
- 期限超過状態
- 週・月の期間境界
- 完了数、必要回数、残り回数
- 表示可否と非表示理由
- 通知候補時点

### 11.2 範囲指定

無期限TODOを無制限に展開してはならない。

- 日付別一覧: 選択した1論理日
- カレンダー: 表示月と週表示に必要な前後日
- 通知: 通知処理が要求する有限期間
- 整合処理: 保存済み処理位置から現在直前までの有限チャンク
- カテゴリ別一覧: 実行日を展開せず、TODO定義と現在期間の進捗を1件として返す

### 11.3 計算結果

計算結果には少なくとも次を含める。

- TODO ID
- 対象論理日
- 対象カテゴリ情報
- 実行対象か
- 期限時点
- 未完了、期限超過、完了、スキップ
- 現在期間と進捗
- 残り回数
- 非表示理由
- 使用したTODO定義リビジョン

非表示理由は少なくとも次を区別する。

- 有効期間外
- 対象曜日または指定日ではない
- 祝日のため除外
- 完了済み
- スキップ済み
- 必要回数達成済み
- アーカイブ済み
- 終了済み

## 12. 共通利用

- TODO一覧は計算エンジンが返す対象と期限を使用する。
- カレンダーは確定履歴と、現在分だけを計算エンジンから取得する。
- 通知は計算エンジンが返した期限時点と通知候補を使用する。
- ウィジェットはRepositoryからTODO一覧と同じ計算結果を取得する。
- 各機能が独自の曜日判定、期間判定、論理日判定を実装してはならない。

## 13. テスト

単体テストでは少なくとも次を網羅する。

- うるう年と2月29日
- 28日、29日、30日、31日の月末
- 毎月31日の存在しない月
- 毎月 第X X曜日の複数指定と、第5曜日が存在しない月
- 一定日数ごとの開始日基準
- 7種類の週開始曜日
- 最初と最後の部分期間
- 祝日取得済み、未取得、取得失敗
- 終了時刻0:00と1:00～23:00
- 終了時刻と期限が同じ場合
- 終了時刻より前後の期限
- タイムゾーン変更
- 夏時間の欠落時刻と重複時刻
- 必要回数達成、超過、取り消し
- 編集、アーカイブ、復元
- 長期未起動

ランダムな日付範囲を使い、少なくとも次の不変条件も検証する。

- 同一TODOを同一論理日へ重複生成しない。
- 有効期間外へ実行対象を生成しない。
- 必要回数達成後に追加完了できない。
- 確定済み履歴を再計算で変更しない。
- 同じ入力に対する結果が常に一致する。

## 14. 受け入れ条件

1. 全繰り返し方式をstartDate基準で決定的に算出できる。
2. カテゴリごとの終了時刻から論理日と期限を正しく算出できる。
3. 月末、祝日、夏時間、タイムゾーン変更を一貫して扱える。
4. 週X回・月X回の部分期間、進捗、期間結果を算出できる。
5. 無期限TODOを無制限にメモリへ展開しない。
6. TODO一覧、カレンダー、通知、ウィジェットが同じ計算結果を利用できる。
7. 計算処理をAndroidなしのローカル単体テストで検証できる。

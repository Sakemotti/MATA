## 1. 目的

入力誤り、端末内データ、OS機能、外部サービスおよび予期しない障害を一貫して扱い、ユーザーが原因、影響、次に行える操作を理解できるようにする。失敗時は確定済みデータを維持し、重複処理、無限再試行および暗黙のデータ削除を防ぐ。

## 3. 基本方針

1. ユーザー操作の成否は、永続化または外部処理の確定後に表示する。
2. 失敗した操作を成功したように見せず、楽観的表示を行った場合は確定状態へ戻す。
3. エラー表示には「何が失敗したか」「影響」「次にできること」を含める。
4. 例外名、HTTP状態、SQL、スタックトレース、SDK内部コードをユーザーへ直接表示しない。
5. 再試行は冪等性を保証できる処理だけに行い、購入、復元、削除などを二重実行しない。
6. 通信できなくてもTODO、カテゴリ、履歴および設定の端末内基本機能を継続する。
7. データベース障害や移行失敗を理由に、ユーザー確認なしでデータを削除・再作成しない。
8. ユーザー向け文言と診断情報を分離し、個人情報をログへ含めない。

## 4. 共通状態モデル

画面または処理は必要に応じて次の状態を明示的に持つ。

- `Idle`: 未開始
- `Loading`: 初回取得中
- `Content`: 正常な内容を表示中
- `Empty`: 正常に取得でき、対象データが0件
- `Refreshing`: 既存内容を維持した再取得中
- `Submitting`: 保存、完了、削除などの実行中
- `RecoverableError`: 再試行または代替操作が可能
- `BlockingError`: 対象機能を安全に継続できない
- `Completed`: 一度だけ消費する完了結果

- `Empty`と取得失敗を同じ表示にしない。
- 既存内容を表示できる再取得失敗では、内容を消さず非遮断型のエラーを表示する。
- 同じ一時イベントをActivity再生成後に重複表示しない。

## 5. 責務

- data層は技術例外を分類済みの失敗型へ変換する。
- domain層は業務ルール違反、競合、対象消失、権限不足を表現する。
- ViewModelは失敗型から画面状態とユーザー操作へ変換する。
- UIは分類済みの表示モデルだけを扱い、例外メッセージを解釈しない。
- 外部SDKのエラーコードはAdapter内でアプリ共通の失敗型へ変換する。

- 対象ソースcommit: `e57ababd3b6fb4ad12bf57dada776e9189288dbc`

- 項目別結果: [initial-release-results.tsv](initial-release-results.tsv)
- 実施台帳: [初回Closed testing実施台帳](closed-testing-log.md)

## 1. 割り当て方針

総合動作確認項目403件を、実施方法に応じて次の3レーンへ分ける。

| レーン | 担当 | 件数 | 対象 |
| --- | --- | ---: | --- |
| `CLOSED_TESTER` | `T01`〜`T12` | 276 | `UI`、`MANUAL`または`E2E`を含み、実機利用で確認できる項目 |
| `DEV_AUTO` | `DEV` | 100 | UNIT、Repository、DB、計算、通知スケジューラ等の技術検査 |
| `RELEASE_OWNER` | `OWNER` | 27 | CI、署名、Google Play、法的文書、公開判定等の`REL`項目 |

すべての試験IDに主担当を1件だけ設定する。これは責任範囲の重複を避けるための主担当であり、他のテスターが同じ操作を行うことを禁止しない。全テスターは担当項目とは別に、参加ガイドの基本操作をスモーク確認する。

`DEV_AUTO`のうち、論理日・期限・繰り返し計算26件、履歴確定・取り消し・復元・完全削除8件、通知候補・登録・再構成11件の計45件は[自動試験証跡TSV](automated-test-evidence.tsv)でJUnitテストと1対1に対応済みである。残る項目は、専用テストと対応表が揃うまで既存テストの包括的な成功だけで合格にしない。

## 3. 全員共通のスモーク確認

次の操作は正式な主担当とは別に全員が行い、端末差や通常利用時の問題を拾う。

1. Google Playからインストールまたは更新し、通常起動する。
2. カテゴリと単発TODOを登録する。
3. 繰り返しTODOを1件登録する。
4. TODOを1件完了し、別の1件をスキップする。
5. カレンダー履歴を確認する。
6. アプリを終了・再起動し、登録内容が残っていることを確認する。
7. 気付いた表示崩れ、分かりにくさ、クラッシュ、応答停止を報告する。

## 4. 実施手順

1. `OWNER`が[初回Closed testing実施台帳](closed-testing-log.md)の端末欄へ`T01`〜`T12`を登録する。
2. 端末特性を見て、通知、ウィジェット、最大フォント、TalkBack、タブレット等の環境担当を確定する。
3. 各テスターへ[参加ガイド](closed-testing-tester-guide.md)と、自分のIDで絞り込んだ試験IDを渡す。
4. 報告を受けたら実施台帳へ実施IDを追加し、[項目別結果TSV](initial-release-results.tsv)へ結果と証跡を反映する。
5. 不合格はIssueを作成し、修正版で同じ試験IDを再試験する。
6. 定期的に割り当てと結果を検証し、未実施のP0/P1を優先して再配分する。

## 5. 検証

```powershell
node tools/test-specs/verify-assignments.mjs
node tools/test-specs/verify-results.mjs
node tools/test-specs/verify-automated-evidence.mjs
```

割り当て検証は、403件のID漏れ・重複、仕様書との優先度・種別不一致、不適切なレーン、無効な担当IDおよび担当件数を確認する。試験結果検証は別途、結果値と証跡の整合性を確認する。

## 6. 再配分

- 端末や権限の都合で実施できない場合、同じレーンの別テスターへ主担当を変更してよい。
- `CLOSED_TESTER`を`DEV_AUTO`へ変更して未実施を解消したことにはしない。エミュレータで代替する場合も、項目が要求する実機条件を満たすか確認する。
- `DEV_AUTO`または`RELEASE_OWNER`を外部テスターへ移さない。
- 担当変更後は割り当て検証を実行し、実施台帳に変更理由を残す。
